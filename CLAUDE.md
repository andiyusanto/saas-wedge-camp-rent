## 1. Apa project ini

SaaS tools operasional untuk UKM rental alat kamping/outdoor di **seluruh Indonesia** (pilot/validasi pertama di Malang Raya — Kota Malang, Kabupaten Malang, Kota Batu, lihat bagian 3), dengan rencana jangka panjang berkembang jadi marketplace publik — tapi **belum sekarang**.

**Project ini terpisah dari `bilbo-outdoors`** (repo lain milik owner yang sama). Tidak ada relasi kode atau data antara keduanya, kecuali kemungkinan pola stack teknis yang mirip.

### Nama produk
- **Sewalog** — nama produk SaaS-tool fase sekarang. Ini nama yang tampil di UI aplikasi (header, judul halaman, dsb), bukan cuma istilah internal. Nama repo `saas-wedge-camp-rent` sifatnya teknis saja, jangan dipakai sebagai nama tampilan.
- **Rimbasewa** — nama produk marketplace fase nanti (belum aktif, lihat bagian 2). Jangan dipakai di UI sebelum fase marketplace resmi dimulai.

## 2. Strategi produk — kenapa urutannya begini

Marketplace rental dua sisi (vendor + penyewa) yang langsung dibangun dari awal secara historis susah scale di Indonesia (contoh: Rentist, Cumi, Raggam — cold-start problem dua sisi sekaligus). Strategi yang lebih terbukti (dipakai Sewasam, MyRental): **bangun basis vendor dulu lewat tools operasional yang berdiri sendiri nilainya**, baru nyalakan marketplace di atas basis itu.

Urutan fase:
1. **Fase sekarang — SaaS-wedge**: tools gratis/uji coba untuk vendor kelola stok, transaksi, jaminan, denda. Tanpa embel-embel marketplace ke vendor di tahap ini.
2. **Fase nanti — Marketplace** (belum dimulai, tidak ada tanggal pasti): dibuka setelah ada bukti vendor pilot beneran pakai tools secara rutin. Skema database sudah disiapkan untuk fase ini (`business_profiles`, `marketplace_consents`) tapi belum diaktifkan secara fungsional.

**Jangan bangun fitur marketplace publik (listing, pencarian lintas vendor, dsb) sebelum ada instruksi eksplisit** — meski skemanya sudah ada, itu persiapan struktural, bukan sinyal untuk mulai build sekarang.

## 3. Target pengguna & scope wilayah

- Pemilik/staf UKM rental alat kamping — bukan technical user, butuh UI yang sangat sederhana dan minim friksi.
- Cakupan pengguna: **seluruh Indonesia** — bukan lagi dibatasi ke Malang Raya (rencana lengkap di `knowladge/marketing-plan-2026-q4.md` bagian 2). Data referensi wilayah (field "Kota" di profil usaha) sudah mencakup seluruh Indonesia sejak migration 033 (lihat bagian 7).
- **Malang Raya tetap kelompok validasi/pilot PERTAMA** — vendor prioritas: Jawa Timur Outdoor, Kubu Barat Camp Rental (Gelombang 1 — dikunjungi langsung, peluang aktivasinya paling tinggi), Merbabu Outdoor Malang, Wildtrack Adventure (Gelombang 2 — via DM dulu).
- **Vendor di luar Malang Raya** diajak dan di-onboard **jarak jauh** (chat/DM, video call) — bukan kunjungan fisik.
- **Harga: gratis sampai 31 Desember 2026.** Harga setelahnya belum ditentukan — rencananya diumumkan sebelum tanggal itu. Jangan janjikan angka harga ke vendor sebelum benar-benar diputuskan.

## 4. Tech stack

- Frontend: React
- Backend: Express
- Database & Auth: Supabase (Postgres + RLS)
- Platform: **Web app, mobile-first** — bukan native Android/iOS untuk tahap ini.
- Zona waktu: **WIB (UTC+7)** sebagai default — lihat penjelasan di bawah.

### Kenapa web, bukan native app
Distribusi ke vendor harus nol-friksi (kirim link, langsung buka browser — bukan sideload APK atau app store review) karena vendor masih tahap "coba dulu tanpa komitmen". Kecepatan iterasi juga lebih penting di fase validasi daripada pengalaman native.

### Kenapa mobile-first, bukan cuma responsive
Pemakaian nyata terjadi sambil berdiri di depan rak alat, pelanggan menunggu di depan — bukan di depan laptop. Desain alur inti (kalender, catat transaksi, tracking denda) dari mobile dulu, desktop jadi lapisan kedua untuk kebutuhan sekunder (rekap, setup katalog awal).

### Soal app-like / PWA
Boleh tambahkan manifest + ikon agar bisa "Add to Home Screen" (biaya kecil, murni penambahan). **Jangan implementasi offline-first caching agresif** — data stok yang di-cache offline berisiko menampilkan info basi ke vendor, yang justru menciptakan ulang masalah double-booking yang coba diselesaikan tools ini. Tunda sampai ada strategi caching yang jelas soal validitas data.

**Tombol "Pasang Aplikasi" & tutorial Panduan** (11 Nov 2026, `research/brief-panduan-sinkron-dan-pasang-aplikasi-2026-11.md`) — Navbar punya tombol instal (ikon unduh dekat tombol Keluar, `useInstallPrompt.ts`/`InstallAppButton.tsx`): Android/desktop lewat `beforeinstallprompt` bawaan browser, iPhone/iPad Safari (tidak punya API instal) dapat petunjuk manual "Bagikan → Tambah ke Layar Utama". Tombol otomatis hilang kalau sudah standalone atau browser tidak mendukung instal. Panduan punya bagian baru "Pasang Sewalog di Layar Utama" (bagian 1b) dengan ilustrasi 4 perangkat. `App.tsx` mendaftarkan `sw.js` sejak mount (bukan cuma lewat `usePushNotifications.ts`) supaya tombol instal installable sejak awal — **sw.js sendiri TIDAK diubah**, tetap cuma handler `push`/`notificationclick`, tanpa `fetch`/cache apa pun (prinsip di atas tidak berubah).

### Zona waktu — kenapa WIB dihardcode, bukan ikut timezone server

**Update 9 Nov 2026 — zona waktu per rental (migration 053).** Sejak vendor di luar WIB mendaftar (mis. Balikpapan, WITA), WIB tidak lagi satu-satunya zona: `businesses.timezone` (`Asia/Jakarta` WIB default / `Asia/Makassar` WITA / `Asia/Jayapura` WIT), diatur owner di Kelola Usaha (ada saran berdasarkan provinsi, tidak pernah diganti otomatis). Semua rental lama tetap WIB sampai owner menggantinya. Prinsip di bawah tetap berlaku — offset dihitung manual (Indonesia tanpa DST), TIDAK pernah ikut timezone server — cuma offset-nya sekarang dari zona rental: di backend pakai `todayInTz()`/`toDateStrInTz()`/`tzOffsetIso()` dari `dates.ts` dan `computeDueAt(..., timezone)` untuk kode yang tahu business-nya; `todayInWIB()` cuma untuk kode tanpa konteks rental (demo, impor Excel). Di database: `create_booking_request`, `get_public_availability` membaca `businesses.timezone`; `get_public_page`/`get_public_ordering_page`/`get_booking_request_status` mengirim `timezone` (min tanggal ambil di Etalase dihitung server, jam batas konfirmasi tampil "WITA"/"WIT"). **Sengaja tetap WIB**: masa aktif/tenggang langganan (044/045 — tagihan Sewalog, bukan operasional rental). Mengganti zona tidak di-snapshot per transaksi: transaksi yang masih aktif ikut dihitung ulang dengan zona baru (koreksi ke arah benar, selisih 1–2 jam), denda yang sudah tercatat tidak berubah.

Vendor pilot awal ada di Malang Raya (lihat bagian 3), jadi **WIB (UTC+7) adalah default timezone aplikasi** (lihat update migration 053 di atas untuk WITA/WIT). Perhitungan "hari ini" untuk status booking (aktif/dipesan), ketersediaan kalender, dan due-date denda keterlambatan di backend **sengaja dihitung lewat offset WIB tetap** (`backend/src/lib/dates.ts`, `backend/src/lib/penalty.ts`), bukan lewat `Date` lokal server — karena server bisa saja di-deploy di region/timezone berbeda (mis. Render), dan kalau perhitungan tanggal ikut timezone server, status booking/ketersediaan bisa bergeser satu hari tergantung di mana server jalan. Frontend sebaliknya sengaja pakai waktu lokal **browser** (`todayStr()` di `frontend/src/utils/formatters.ts`) — device vendor secara fisik ada di WIB, jadi waktu lokal browser sudah benar tanpa perlu offset manual.

**Kalau nambah logika baru yang melibatkan tanggal/waktu**: di backend, selalu lewat `todayInWIB()`/`addDays()` dari `dates.ts` (jangan `new Date().getDate()`/`setDate()` langsung — itu ikut timezone server, bukan WIB). Skrip demo (`backend/src/lib/demoReset.ts` dan `scripts/seed-demo.mjs`) pernah kena bug ini (`todayPlus()` pakai `Date` lokal + `toISOString()`, tercampur), sudah diperbaiki — jangan diulangi polanya di kode baru.

**Update 14 Nov 2026 — batas jam kembali tetap (migration 062).** `businesses.return_deadline_time`/`return_deadline_next_day` (nullable, null = ikuti jam ambil, perilaku sebelum fitur ini) — owner atur di Kelola Usaha, dekat Toleransi telat. Diisi -> `computeDueAt()` (`backend/src/lib/penalty.ts`) memakai jam TETAP itu (end_date, atau end_date+1 kalau "hari berikutnya") di zona rental, bukan jam ambil barang — Toleransi telat (jam) tetap berlaku DI ATAS due ini TANPA PERUBAHAN (`computeLateBlocks`/`computeLateFee`/`computeTieredLateFee` sama sekali tidak disentuh). **Definisi "00:00"/"24:00" (disengaja, bukan default alami)**: SELALU dibaca `end_date+1` pukul 00:00, TERLEPAS dari nilai `return_deadline_next_day` yang tersimpan — tidak pernah dobel jadi `+2` hari. "24:00" tidak pernah disimpan literal, form `BusinessInfoSection.tsx` menormalkannya jadi `"00:00"` + mengunci toggle "hari berikutnya" (tercentang, disabled) sebelum dikirim — satu representasi kanonik, bukan dua state yang bisa dikombinasikan bebas. **Jaring pengaman**: kalau due hasil hitung <= jam ambil sungguhan (mis. ambil jam 23:00, batas tetap 22:00 di hari yang sama) — `computeDueAt()` menggeser due +1 hari (jam tetap sama) supaya transaksi tidak pernah langsung "terlambat" detik itu juga saat diambil; `NewBookingModal.tsx` juga menampilkan peringatan non-blocking kalau kombinasi tanggal/jam ambil membuat batasnya sudah lewat (dihitung dari waktu lokal browser, bukan sumber kebenaran — backend yang menegakkan).

`bookings.return_deadline_time`/`return_deadline_next_day` adalah SNAPSHOT saat transaksi dibuat (pola sama `rental_day_mode` migration 049) — mengganti setting ini di Kelola Usaha tidak mengubah ulang transaksi yang sudah ada. Pesanan Online yang dikonfirmasi ikut ter-snapshot otomatis (lewat form Catat Transaksi/`POST /bookings` yang sama, tidak ada jalur terpisah). Ditampilkan sebagai baris "Kembali paling lambat" di struk WhatsApp, Nota Sewa cetak, halaman Etalase publik, dan halaman status pesanan (`get_public_page`/`get_booking_request_status`, migration 062) kalau diisi — kosong (null) berarti baris itu tidak muncul sama sekali, sama seperti sebelum fitur ini ada.

## 6. Fitur inti MVP (urutan prioritas build)

1. **Kalender ketersediaan** — list per-item dengan strip status beberapa hari ke depan (bukan grid kalender bulanan penuh). Ketersediaan **dihitung on-the-fly**, tidak disimpan sebagai tabel terpisah — lihat catatan di `skema-final.sql`.
2. **Catat transaksi** — form input cepat: nama penyewa, kontak, pilih alat (multi-item), tanggal ambil/kembali, jenis jaminan, total harga. Minim ketikan, karena diisi sambil melayani pelanggan yang menunggu.
3. **Transaksi Aktif (tracking jaminan & denda)** — daftar transaksi aktif dengan status (telat/rusak/hilang), dan **dua jenis denda dipisah eksplisit**: denda keterlambatan vs denda kerusakan/kehilangan (bisa muncul bersamaan dalam satu booking, jangan digabung jadi satu angka). Nama tab di UI sengaja "Transaksi Aktif" (bukan "Jaminan & Denda") — lebih mencerminkan fungsi utamanya (tracking siklus transaksi: ambil-kembali), bukan cuma dua sub-perhatian finansial di dalamnya.

Fitur di luar tiga ini (rekap laporan, manajemen multi-cabang, marketplace publik) **belum masuk MVP** — jangan ditambahkan tanpa validasi kebutuhan dari pilot.

**Etalase Online** (dibangun September 2026, di luar tiga fitur inti di atas) — halaman publik read-only per vendor, tanpa login, murni katalog alat + info kontak (jam operasional, alamat, tombol WhatsApp). **Bukan marketplace** — tidak ada pencarian/browsing lintas vendor (satu halaman = satu vendor, isinya data yang sama yang sudah mereka input untuk manajemen internal), dan **tidak ada pembayaran di halaman ini**; pemesanan hanya lewat formulir "Pesanan Online" opsional (default OFF, lihat paragraf di bawah), bukan checkout otomatis. Awalnya sengaja dipisah dari tab **Toko Online** (lihat non-goal storefront+payment di bagian 8) — "Etalase" (lihat-lihat, sudah bisa dipakai sekarang) vs "Toko" (transaksi sungguhan, masih dievaluasi) beda maknanya. Tab **Toko Online** sendiri DISEMBUNYIKAN dari Navbar sejak 2 Nov 2026 (permintaan Andi, `SHOW_TOKO_ONLINE_TAB` di `frontend/src/components/Navbar.tsx`, tinggal diubah ke `true` untuk menampilkan lagi) — maknanya sudah tumpang-tindih dengan fitur Pesanan Online yang sekarang sungguhan ada di Etalase, bukan cuma fake-door kosong lagi. Komponennya (`OnlineStoreScreen.tsx`) dan Panduan-nya TIDAK dihapus, cuma ikut disembunyikan lewat flag yang sama. Pemrosesan pembayaran online tetap non-goal (bagian 8) terlepas dari status tampil/sembunyi tab ini. Data disimpan di tabel `public_pages` (migration 019), **terpisah dari `business_profiles`** supaya tidak mencampur consent "vendor punya etalase publik" dengan consent opt-in Rimbasewa (lihat bagian 7). Halaman publiknya sendiri di-render langsung oleh backend Express (`backend/src/routes/etalase.ts`) sebagai HTML string per-request — bukan route React (frontend 100% di belakang login, tanpa client-side routing) dan bukan file statis ala `landing/public/blog/*.html`, karena Open Graph tags wajib ada di HTML mentah tanpa JS supaya preview link WhatsApp benar, dan backend adalah satu-satunya proses live di stack ini yang bisa mencerminkan perubahan publish/edit vendor secara langsung.

URL publiknya sengaja BUKAN di bawah domain backend "api" (mis. `api.sewalog.com/toko/{slug}`) — subdomain "api" salah kesan buat halaman yang justru dilihat pelanggan vendor, bukan dipanggil programatik. Kalau custom domain `toko.sewalog.com` sudah disambungkan (env `TOKO_PUBLIC_HOST`, lihat README bagian Deploy langkah 8), URL-nya jadi `toko.sewalog.com/{slug}` langsung — SATU Web Service Express yang sama menjawab dua domain sekaligus, dibedakan lewat header `Host` di `routes/etalase.ts` (`req.hostname`), bukan proses/deploy terpisah. Jalur lama `/toko/{slug}` di domain backend asli tetap selalu aktif sebagai fallback (dev lokal, atau kalau custom domain belum disambungkan).

**Gambar & teks pratinjau link Etalase** (9 Nov 2026) — `og:image` Etalase BUKAN lagi `logo_url` mentah (WebP ~512px: WA/Telegram cuma menampilkan thumbnail kecil, sebagian aplikasi tidak merender WebP), melainkan PNG 1200×630 dari route `GET /og/{slug}.png` (`backend/src/lib/shareCard.ts`): logo vendor dikonversi di tengah latar putih (permintaan Andi, seperti Sewascale), atau kartu teks nama rental + kota kalau belum ada logo. Font kartu teks = Roboto (`backend/assets/fonts`, OFL) karena sewalog.com memakai `system-ui`/Roboto — jangan ganti ke font lain tanpa diskusi. Hasil di-cache di R2 (`og-cards/v1/{hash}.png`, dibaca lewat API R2, BUKAN domain publik — lewat domain publik Cloudflare sempat menyimpan 404 lama). Judul share "Sewa Alat Camping {nama} — {kota}", deskripsi berubah sesuai Pesanan Online aktif/tidak, plus tag `twitter:` lengkap. Halaman status pesanan cuma memakai gambar vendor yang sama — tetap tanpa data pelanggan, tetap `noindex`.

**Pencarian ketersediaan per rentang tanggal** (ditambahkan segera setelah rilis awal, lalu direvisi dari satu tanggal jadi rentang) — halaman `/toko/{slug}` (atau `toko.sewalog.com/{slug}`) juga punya dua date-picker (tanggal ambil & kembali) yang menampilkan **jumlah unit tersisa persis** per alat, lewat fetch JS ke `GET /api/public/etalase/{slug}/availability?start_date=...&end_date=...` (RPC `get_public_availability`, migration 021 — signature rentang, menggantikan versi satu-tanggal di migration 020). Angka yang dibalikkan adalah titik TERBURUK (remaining minimum) di sepanjang rentang, dihitung per-hari persis seperti validasi kapasitas `POST /bookings` (`routes/bookings.ts`) — satu tanggal saja tidak cukup karena alat bisa tersedia di hari pertama tapi habis di hari ketiga dalam periode sewa yang sama. Exposure jumlah unit tersisa persis ini **pembalikan sadar** dari sikap awal "`total_units` selalu privat, cuma ajakan 'Hubungi kami untuk cek ketersediaan'" — vendor pemilik produk (bukan hasil observasi/asumsi Claude) secara eksplisit memilih exposure paling terbuka dari tiga opsi yang ditawarkan (tanpa cek / status kasar tersedia-terbatas-penuh / jumlah persis). Kalau nanti mau ditarik lagi ke exposure lebih tertutup, lihat komentar keputusan di `migrations/021_public_availability_range.sql`.

**Jeda persiapan per-alat** (`items.readiness_hours`, migration 026 lalu direvisi migration 028) — diadaptasi dari fitur `readinessHours` Bilbo-Outdoors (referensi produk sejenis, owner sama) setelah membandingkan dua fix bug Bilbo yang menutup celah waktu Sewalog sendiri sebelumnya sama sekali tidak punya fiturnya. Satu angka per alat dalam JAM (default 0 = tidak ada jeda, tersedia lagi hari yang sama), diisi lewat form Katalog & Stok Alat — berapa jam alat butuh dibersihkan/dicek sebelum siap disewa lagi setelah kembali. **Awalnya sempat dibangun dalam satuan HARI (migration 026)**, direvisi ke jam atas permintaan eksplisit karena banyak alat (headlamp, kompor) bisa dibersihkan jauh di bawah sehari, dan sejak `bookings.picked_up_at`/`actual_return_at` jadi instant asli (migration 027, 003), jam jadi satuan input yang lebih jujur merepresentasikan kebutuhan vendor.

**PENTING — ini BUKAN presisi sub-hari.** Blocking-nya sendiri tetap per TANGGAL KALENDER (Kalender Ketersediaan sengaja strip-per-hari, bukan grid per-jam — lihat bagian 5). Jam dikonversi ke hari pembulatan-ke-atas (`Math.ceil(hours/24)`) sekali di titik pemakaian — diverifikasi langsung dari `server.ts` Bilbo (bukan diasumsikan): `readiness_hours=0` → tidak diblokir sama sekali, tersedia lagi hari yang sama barang kembali; 1-24 jam → blokir PERSIS hari kembali itu sendiri (tersedia mulai besok); 25-48 jam → blokir hari kembali + 1 hari lagi; dst. Manfaat satuan jam murni sebagai unit input yang lebih wajar dan pembulatan yang lebih tepat, BUKAN klaim ketersediaan-parsial-di-tengah-hari.

Diterapkan **simetris** di `usedUnitsOn()` (`backend/src/lib/availability.ts`) untuk booking `dipesan` (belum diambil, belum ada instant asli buat dijangkarkan): mundur sebelum `start_date` DAN maju setelah `end_date`, bukan cuma maju saja — referensi Bilbo sendiri sempat cuma menerapkan sepihak sampai diperbaiki 2026-09-13. Untuk booking `telat`/`selesai` yang SUDAH DITUTUP (punya `actual_return_at` asli), jendela jeda dijangkarkan ke **hari sungguhan barang kembali** (WIB, lewat `toWibDateStr()`), bukan `end_date` terjadwal — lebih akurat untuk pengembalian yang telat jauh dari jadwal. **`selesai` (pengembalian tepat waktu) ikut dihitung** — celah dari migration 026 (readiness diam-diam cuma berlaku buat yang telat, tidak pernah buat yang tepat waktu, karena kebutuhan jeda fisik tidak peduli status telat/tidaknya) ditutup di sini. `get_public_availability()` (Etalase Online) WAJIB ikut menghitung persis sama — dua jalur itu harus selalu sepakat, lihat catatan lengkap di `usedUnitsOn()`.

**Jam pengambilan sungguhan** (`bookings.picked_up_at`, migration 027) — deadline denda telat (`computeDueAt()`, `backend/src/lib/penalty.ts`) sebelumnya selalu dihitung dari jam `created_at` (jam booking DICATAT staff), bukan jam barang benar-benar diambil fisik. Untuk booking yang langsung `aktif` saat dibuat (walk-in) dua jam itu praktis sama, tapi untuk booking `dipesan` yang diambil BELAKANGAN lewat `POST /bookings/:id/pickup`, `created_at` bisa selisih berhari-hari dari momen ambil sungguhan — endpoint pickup itu sebelumnya sama sekali tidak menyimpan jam ambil nyatanya. Ditutup dengan kolom `picked_up_at`, distempel di dua titik (langsung saat dibuat kalau `status='aktif'`, atau di `/pickup` untuk booking yang dipesan duluan) — `computeDueAt()` sekarang memakainya kalau ada, jatuh balik ke `created_at` cuma untuk baris lama dari sebelum migration ini. Sisi pengembalian (`actual_return_at`, migration 003) sudah benar sejak awal — ini menutup celah yang sama di sisi pengambilan, pola yang sama seperti `pickedUpAt` Bilbo-Outdoors.

**Denda kerusakan/kehilangan per-alat** (`penalties.item_id`, migration 029) — diadaptasi dari Bilbo-Outdoors, yang menautkan tiap entri denda ke `productId` spesifik dalam order, bukan cuma ke booking secara keseluruhan seperti Sewalog sebelumnya (masalah nyata untuk transaksi multi-item: sebelum ini, denda kerusakan pada satu alat di antara tiga alat yang disewa tidak bisa dibedakan asalnya dari mana). Kolom nullable, cuma bermakna untuk `type` `kerusakan`/`kehilangan` — `keterlambatan` selalu `item_id=null` karena murni soal keterlambatan pengembalian keseluruhan, tidak masuk akal ditautkan ke satu alat dalam booking multi-item. Divalidasi server-side di kedua endpoint yang bisa membuat baris `penalties` (`POST /bookings/:id/return` dan `POST /bookings/:id/penalties` ad-hoc, `backend/src/routes/trackings.ts`) — `item_id` yang dikirim harus benar-benar ada di `booking_items` booking itu sendiri, ditolak kalau tidak. Di frontend, dropdown pilih alat cuma muncul kalau transaksinya multi-item (`AddFineModal.tsx`, `ReturnModal.tsx`) — untuk transaksi satu alat, penautan otomatis tanpa perlu dipilih manual, sesuai prinsip minim friksi di bagian 5. Nama alat lalu ikut ditampilkan di rincian denda (`TrackingScreen.tsx`), struk WA (`generateWhatsAppReceipt()`), dan Nota Sewa cetak (`InvoiceModal.tsx`). Baris `penalties` lama (dari sebelum migration ini) tetap `item_id=null` — tidak di-backfill, setara "tidak spesifik ke alat tertentu".

**Harga bertingkat per-hari** (`items.price_per_day`/`day2_rate`/`day3_rate`/`day4_rate`/`day5_rate`/`extra_day_rate`, migration 034) — diadaptasi dari Bilbo-Outdoors (`src/pricing.ts`, `DayRateTable`), tapi **semantik kolom sengaja beda**: Bilbo simpan TOTAL KUMULATIF per tingkat (`day3Price` = total sewa 3 hari, lookup langsung); di sini tiap kolom adalah TARIF HARI ITU SENDIRI (`price_per_day` = tarif hari 1, `day2_rate` = tarif hari ke-2, dst, `extra_day_rate` = tarif tiap hari ke-6 dst). Alasan beda sengaja: (a) cocok dengan cara vendor mikir harga ("hari 1 Rp30rb, hari 2 Rp20rb, hari 3 dst Rp10rb"), bukan total kumulatif yang harus dihitung sendiri dulu; (b) field kosong di form Katalog & Stok Alat bisa mewarisi tarif tingkat sebelumnya (diresolve sekali saat Simpan, bukan runtime) dan otomatis benar untuk alat flat — kalau mewarisi NILAI KUMULATIF ala Bilbo, alat flat (cuma isi hari 1) akan salah hitung total. Total sewa N hari = jumlah tarif hari 1..min(N,5) + maks(0,N-5) × `extra_day_rate`, dengan N mengikuti mode hitung durasi sewa yang berlaku untuk transaksi itu (per malam atau per hari kalender, lihat **Cara hitung durasi sewa** di bawah) — bukan selalu "hari kalender inklusif" seperti sebelum migration 049. Satu fungsi `computeItemRentalPrice()` dengan bentuk identik di tiga runtime (`frontend/src/utils/formatters.ts`, `backend/src/lib/demoReset.ts`, `scripts/seed-demo.mjs`) — backend `POST /bookings` sendiri TIDAK pernah menghitung ulang/validasi harga (selalu percaya nilai dari client, sama seperti `total_price`), jadi tetap satu sumber kebenaran di sisi klien.

**Cara hitung durasi sewa** (`businesses.rental_day_mode`, migration 049) — pengaturan PER-RENTAL (owner-only, di Kelola Usaha), bukan satu rumus tetap untuk semua vendor. Dua pilihan: `per_malam` (ambil Sabtu, kembali Minggu = 1 hari — DEFAULT untuk semua rental lama & baru, keputusan Andi 2 Nov 2026 karena banyak rental pilot/referensi, mis. Tunggul dan Bilbo-Outdoors, memakai skema ini) atau `per_hari_kalender` (perilaku lama, inklusif — ambil & kembali hari sama = 1 hari). Di mode `per_malam`, ambil dan kembali TIDAK BOLEH di hari yang sama (sama seperti Bilbo) — ditegakkan di tiga titik: Catat Transaksi (date picker + `POST /bookings`), form Pesanan Online di Etalase (`bookingRequests.ts`), dan RPC `create_booking_request` sebagai jaring pengaman server-side. **Label di UI selalu memakai kata "hari"**, tidak pernah "malam", apa pun mode yang dipilih.

`bookings.rental_day_mode` (nullable) adalah SNAPSHOT mode yang berlaku SAAT transaksi itu dibuat, bukan pointer ke pengaturan business yang sedang berlaku — begitu vendor ganti pengaturan ini, transaksi yang sudah ada (nota, struk WA, ekspor Riwayat, dan denda telat bertingkat lewat `rentDuration`) tetap dihitung dengan mode SAAT DIBUAT, tidak pernah dihitung ulang. `null` (baris dari sebelum migration ini) ditafsirkan `per_hari_kalender` oleh `rentalDuration()`/`rentalDays()` — PERSIS perilaku lama, bukan nilai baru yang kebetulan sama. Sengaja TIDAK diubah: `computeDueAt()`/batas telat (sudah 24 jam dari jam ambil, otomatis konsisten di bawah `per_malam`), Kalender Ketersediaan/`usedUnitsOn()`/`get_public_availability` (hari kembali tetap dihitung hari terpakai di kalender terlepas dari mode ini), dan `readiness_hours`.

Model lama (migration 009, `discount_min_days`/`discounted_price_per_day`) dibackfill ke tarif per-hari lewat formula: tarif hari ke-k = `price_per_day` kalau `k <= discount_min_days`, selain itu `discounted_price_per_day` (coalesce ke `price_per_day`) — secara matematis identik dengan total lama untuk setiap N, jadi item yang tidak sengaja diubah tetap menghasilkan total yang SAMA PERSIS seperti sebelumnya. Kolom lama **sengaja TIDAK di-drop** di migration 034 — migrasi dijalankan manual oleh pemilik produk, ada jeda nyata sebelum kode baru dideploy, jadi kode lama yang masih baca dua kolom itu tidak boleh langsung rusak. Drop keduanya ditunda ke migration terpisah SETELAH kode baru confirmed live (lihat TODO di file migrasinya).

Subtotal per `booking_items` (`booking_items.subtotal`, migration 034, nullable) disnapshot SEKALI saat transaksi dibuat (frontend hitung lewat `computeItemRentalPrice()`, backend simpan apa adanya) — Nota Sewa cetak dan struk WA selalu baca `subtotal` ini, BUKAN menghitung ulang dari harga katalog item saat struk ditampilkan, supaya breakdown per-alat di struk tidak diam-diam berubah kalau vendor mengedit harga alat itu setelah transaksinya selesai (prinsip "beku" yang sama seperti `price_at_booking`/`bookings.total_price`). Baris lama (`subtotal=null`, dari sebelum migration ini) fallback ke `price_at_booking * quantity * hari` di `InvoiceModal.tsx`/`generateWhatsAppReceipt()` — perilaku yang sama seperti sebelum fitur ini ada (dua tempat itu ternyata SUDAH salah sejak migration 009, mengabaikan diskon sama sekali di breakdown per-baris meski total keseluruhan tetap benar — celah yang baru ketahuan & ditutup lewat perbaikan ini).

**Denda keterlambatan bertingkat** (`booking_items.day2_rate_at_booking`..`extra_day_rate_at_booking`, migration 034) — revisi dari keputusan awal "denda keterlambatan tidak pernah tahu soal tingkat harga ini": vendor pilot punya pola nyata di mana tarif hari tambahan jauh lebih murah dari hari pertama (contoh TND-01: 30rb/20rb/10rb), dan denda telat flat (selalu pakai tarif hari-1) terlalu mahal untuk kasus itu — diadaptasi dari rumus MARGINAL Bilbo-Outdoors (`server.ts` endpoint `calculate-late`: `harga(durasi+telat) - harga(durasi)`), diverifikasi langsung dari source-nya, bukan diasumsikan. Snapshot 5 kolom `*_at_booking` diisi SERVER-SIDE di `POST /bookings` dari `items` SAAT ITU (pola sama seperti `price_at_booking`, BUKAN trust-the-client seperti `booking_items.subtotal`) — supaya denda telat tidak pernah baca harga katalog yang sudah vendor edit setelah transaksi dibuat.

Mekanisme toleransi/blok 12-jam-50% Sewalog yang sudah ada (`backend/src/lib/penalty.ts`) **sengaja TIDAK diubah cara hitung jumlah blok/harinya** — beda dari model Bilbo sendiri yang pakai hari 24-jam utuh (`Math.ceil(hoursLate/24)`). `computeTieredLateFee()` menggabungkan keduanya: `blocks` dihitung persis seperti sebelumnya (`computeLateBlocks()`, diekstrak dari `computeLateFee()` lama agar dua rumus selalu sepakat soal jumlah blok), lalu dipecah jadi `fullLateDays = floor(blocks/2)` (hari telat penuh, 100% tarif) + sisa setengah blok kalau `blocks` ganjil (50% tarif hari berikutnya) — tarif per hari diambil dari `computeItemRentalPrice(rentDuration+k) - computeItemRentalPrice(rentDuration+k-1)` (marginal, bisa beda tiap hari), bukan tarif flat. Dihitung PER ITEM lalu dijumlah (beda item bisa beda tarif dalam satu booking multi-item) — kalau snapshotnya null (baris `booking_items` dari sebelum migration 034), fallback ke `computeLateFee()` lama (flat, pakai `price_at_booking`), perilaku identik seperti sebelum fitur ini ada. Untuk item FLAT (semua tingkat sama), rumus baru ini menghasilkan angka SAMA PERSIS dengan rumus lama — diverifikasi matematis, bukan cuma observasi kebetulan — jadi mayoritas item (belum diatur bertingkat) tidak berubah perilakunya sama sekali. Dialog pengembalian (`ReturnModal.tsx`) menampilkan rincian tarif efektif per alat (`late_fee_breakdown` dari `GET /trackings`) di samping saran nominal, bukan nama tingkat yang berpotensi salah.

Etalase Online (`get_public_page()`, migration 020 direplace lagi di migration 034) ikut tampilkan semua tingkat, tapi UI publiknya cuma munculkan satu baris ringkas tambahan ("Mulai Rp X/hari untuk sewa panjang") kalau `extra_day_rate < price_per_day` — alat flat tampil persis seperti sebelumnya, tidak ada baris tambahan.

**Pesanan Online dari Etalase** (dibangun Oktober–November 2026, opsional per vendor lewat toggle "Terima pesanan online" di tab Etalase Online, default OFF) — pelanggan bisa mengirim FORMULIR PESANAN (alat+jumlah, tanggal, nama, WA) langsung dari halaman `/toko/{slug}`, tapi ini **BUKAN checkout/pembayaran online**: keranjang hanya di browser untuk menyusun formulir, tidak ada checkout atau pembayaran, tidak ada payment gateway, dan pesanan BARU menjadi transaksi sungguhan (mengurangi stok, masuk Kalender/Riwayat/omset) setelah vendor menekan **Konfirmasi** lewat form Catat Transaksi biasa (prefill otomatis dari pesanan, tapi jaminan/harga final tetap diisi manual vendor, sama seperti transaksi walk-in) — stok TIDAK pernah ditahan sebelum titik itu (ikut pola MyRental, bukan Bilbo-Outdoors yang menahan stok sejak pesanan masuk). Lihat `research/etalase-online-ordering-plan-2026-10.md` untuk alasan desain lengkap.

Vendor mengatur toggle ini dari kartu "Pesanan Online" di tab Etalase Online (di bawah kartu "Aktifkan Etalase Online", cuma bisa dinyalakan kalau Etalase sudah aktif DAN minimal satu cara bayar aktif, **owner-only** — karyawan tidak bisa mengubah pengaturan ini sama sekali, bukan cuma disembunyikan di UI tapi juga ditegakkan lewat RLS `is_owner_of()` di `public_pages`), termasuk cara bayar yang diterima (Transfer Bank, QRIS statis — gambar diunggah vendor sendiri, atau Tunai saat ambil, bisa lebih dari satu) dan aturan DP (tidak wajib / persen / nominal tetap). **Sewalog tidak pernah memproses pembayaran apa pun** — halaman status pesanan pelanggan (`/pesanan/{token}`, token unguessable) cuma MENAMPILKAN info bayar milik vendor (rekening/QRIS/nominal) SETELAH vendor Konfirmasi, dengan kalimat eksplisit "Pembayaran langsung ke [nama vendor]. Sewalog tidak menerima atau menyimpan dana." — uang tidak pernah lewat Sewalog sama sekali, konsisten dengan batasan arsitektur di `docs/legalitas-pembayaran.md`. Setiap perubahan info bayar tercatat otomatis lewat trigger (`public_page_payment_changes`, append-only, migration 037) — bukan insert manual dari kode aplikasi, supaya tidak bisa terlewat.

Pesanan kedaluwarsa otomatis (lazy, dihitung saat dibaca — bukan cron) kalau vendor tidak merespons dalam 24 jam (atau awal hari tanggal ambil, mana yang lebih dulu) — pelanggan tidak diberi tahu otomatis (tidak ada WA API berbayar di versi pertama), halaman status menjelaskan ekspektasi waktu balas ini. Notifikasi vendor soal pesanan baru: badge angka di tab "Transaksi Aktif" + banner di Kalender Ketersediaan (bagian "Pesanan masuk" di atas daftar transaksi aktif) — **TIDAK LAGI hanya badge/banner dalam-aplikasi**, sejak 11 Nov 2026 vendor juga bisa dapat **notifikasi push (Web Push/VAPID, migration 056)** di perangkatnya langsung, walau Sewalog sedang tidak dibuka — opt-in per perangkat lewat kartu "Notifikasi Pesanan Online" di tab Transaksi Aktif. Isi notifikasi sengaja minimal (nama pelanggan, jumlah alat, tanggal ambil-kembali) — TANPA nomor WA, harga, atau alamat (bisa terbaca di layar kunci). Pengiriman best-effort dari backend lewat `web-push` (`backend/src/lib/webPush.ts`), dipicu setelah `create_booking_request` sukses, TIDAK PERNAH menghalangi/menunda respons ke pelanggan. **Paket minimal/maksimal hari sewa** (`businesses.min_rental_days`/`max_rental_days`, migration 054, 9 Nov 2026) — dari wawancara vendor: Rental Outdoor Cikarang dan Mandalika Outdoor sewa per TRIP (maks 4 hari, harga 1 hari sama dengan 4 hari), bukan per hari lepas. **Ubah Jadwal & Perpanjang** (`booking_reschedules`, migration 055, 10 Nov 2026) — dua aksi terpisah untuk mengubah jadwal transaksi yang sudah dicatat, berlaku untuk semua skema (per hari kalender, per malam, paket). **Ubah Jadwal** (booking berstatus `dipesan`, belum diambil fisik): tanggal ambil DAN kembali boleh berubah, jumlah hari boleh berubah. **Perpanjang** (booking berstatus `aktif`, sudah diambil): hanya tanggal kembali yang maju — batas telat (`computeDueAt`) otomatis ikut geser karena cuma membaca `bookings.end_date`, jadi pelanggan yang minta tambah hari sebelum telat tidak kena denda.

**Ubah Alat pada transaksi berisi paket**: mengubah quantity atau menghapus SATU baris komponen MELEPAS penanda paket untuk SEMUA baris SISA grup `bundle_instance_id` itu (tidak intact lagi) — tapi harga baris lain di grup yang sama TIDAK ikut berubah/redistribusi, cuma porsi baris yang disentuh yang turun/hilang (otomatis dari snapshot rasio di atas: `subtotal = quantity_baru × computeItemRentalPrice(tarif_terskala, hari)`, linear terhadap quantity). Alat BARU yang ditambah tidak pernah dapat penanda. Sebelum Simpan di `NewBookingModal.tsx` (brief "Alat Dalam Paket Dikurangi") perilaku SAMA: rincian komponen per paket punya stepper sendiri (maks = jumlah resep), mengurangi/menghapus salah satu menunjukkan info "Isi paket diubah. Harga dihitung dari porsi paket, label paket dilepas" — alokasi dihitung SEKALI dari resep PENUH (`allocateBundlePrice`), bukan dihitung ulang dari resep yang sudah dikurangi, supaya "jumlah alokasi sisa + porsi yang dihapus = total paket awal" persis. Mengurangi JUMLAH PAKET (×2→×1) ditangani lewat aturan yang SAMA (ubah quantity tiap komponen secara manual) — TIDAK ada kontrol "jumlah paket" khusus di Tahap 1 (dipertimbangkan, sengaja ditunda).

**Simpan Transaksi Atomik, Tahap 1** (17 Nov 2026, `research/brief-simpan-transaksi-atomik-2026-11.md`) — seluruh penulisan `POST /bookings` (customer, booking, booking_items, deposit, barang jual, riwayat status) dipindah dari banyak langkah Express+compensating-delete manual (yang bisa gagal setengah jalan) ke SATU RPC SECURITY DEFINER `create_booking_atomic()` (`migrations/070_create_booking_atomic.sql`): `pg_advisory_xact_lock` per business, cek ulang stok DI DALAM kunci lewat `used_units_on_sql()` (port exact dari `usedUnitsOn()` TypeScript, direvoke dari semua role — cuma bisa dipanggil dari dalam fungsi SECURITY DEFINER lain milik owner yang sama), validasi kepemilikan item/bundle/customer di dalam RPC (karena SECURITY DEFINER bypass RLS), lalu insert semuanya dalam satu transaksi Postgres. Stok tidak cukup melempar SQLSTATE kustom `P0409` (Express memetakannya ke HTTP 409, bukan cocokkan teks error Indonesia). Harga/tarif/alokasi paket TETAP dihitung di TypeScript (Express membangun payload, RPC cuma menulis) — `get_public_availability()` (jalur anon Etalase) SENGAJA TIDAK diganti di tahap ini, dibuktikan sepakat lewat test pembanding titik-batas tidak langsung, bukan berbagi kode. `changed_by` di `booking_status_history` dibaca dari `auth.uid()` di dalam RPC (bukan dari payload — nilai payload bisa dipalsukan member). **3 RPC atomik baru** (pola `apply_booking_item_changes` migration 061 — lock row dulu, baru tulis, satu transaksi Postgres per pemanggilan fungsi):
1. `add_sale_item_stock(p_sale_item_id, p_qty)` — "+ Tambah stok" di Katalog. `stock = stock + p_qty` atomik, BUKAN update langsung dari klien (klien yang menulis nilai absolut bisa menimpa pengurangan stok bersamaan dari transaksi lain) — koreksi manual nilai stok di form Edit TETAP update langsung (nilai absolut, disengaja, dijelaskan di Panduan).
2. `apply_new_booking_sale_items(p_booking_id, p_items)` — dipanggil `POST /bookings` (`routes/bookings.ts`) sebagai LANGKAH TERAKHIR, cuma kalau ada barang jual. Lock SEMUA `sale_items` terkait (`for update`, diurutkan `order by id` — deterministik, cegah deadlock antar transaksi multi-barang bersamaan), cek stok cukup untuk SEMUA baris sekaligus (tolak semua-atau-tidak-sama-sekali), baru kurangi+insert. Gagal → Express melakukan compensating delete (pola unwind yang SUDAH ADA di endpoint ini, bukan ditulis ulang — `POST /bookings` sendiri memang tidak sepenuhnya atomik, cuma bagian sensitif-konkurensi/stok yang dibuat atomik lewat RPC ini). Menolak `sale_item_id` duplikat dalam satu payload (defense in depth — Express SEHARUSNYA sudah menjumlahkan lewat `mergeDuplicateSaleItemRequests()`, `lib/saleItems.ts`).
3. `apply_booking_item_and_sale_changes(p_booking_id, p_new_items, p_new_sale_items, p_new_total_price, p_reason, p_changed_by_name)` — SATU RPC pembungkus untuk Ubah Alat (bukan dua RPC terpisah berurutan dari Express, yang TIDAK atomik — kalau satu sukses satu gagal, stok/isi/total bisa tidak sinkron). Memanggil `apply_booking_item_changes()` yang SUDAH ADA (migration 061/064, TIDAK diubah sama sekali) untuk bagian alat sewa di baris pertama (lock+semua pengecekan berlaku untuk SELURUH transaksi ini termasuk bagian barang jual, karena satu pemanggilan fungsi = satu transaksi), lalu menangani DELTA stok barang jual (qty baru − qty lama: delta positif kurangi+cek cukup, delta negatif KEMBALIKAN) di fungsi yang sama. `total_price` cuma ditulis SEKALI (oleh `apply_booking_item_changes()` di dalam). `name`/`price_at_booking` tiap baris DIPERCAYA dari payload (dihitung Express-side lewat `mergeSaleItemsForUpdate()`, `lib/saleItems.ts` — pola PERSIS `mergeBookingItemsForUpdate()` untuk alat sewa: barang existing pakai snapshot lama, barang BENAR-BENAR BARU pakai harga katalog SAAT INI, resolusi terjadi di Express bukan RPC, supaya RPC tidak diam-diam menimpa snapshot lama dengan harga katalog sekarang tiap kali Ubah Alat disimpan).

**Bagikan Nota sebagai Gambar + perbaikan PDF berhalaman-ganda** (24 Nov 2026, `research/brief-bagikan-nota-gambar-ios-2026-11.md`, dari Wasup Outdoor: "Struk [PDF] hanya bisa diakses melalui PC/laptop, kalau lewat HP cuma kayak gini", iPhone iOS 26.5).

**Investigasi bagian A** (CATATAN: WebKit Playwright TIDAK bisa dijalankan di sandbox sesi app — sistem tidak punya sudo untuk `playwright install-deps`, jadi temuan soal perilaku Safari iOS sungguhan di bawah ini adalah fakta platform WebKit/iOS yang terdokumentasi luas, BUKAN hasil reproduksi langsung sesi ini): (1) `window.print()` di dalam PWA standalone iOS ("Pasang Aplikasi" dari layar utama) dikenal luas TIDAK memunculkan dialog apa pun (WKWebView tanpa chrome Safari) — ini kemungkinan BESAR penyebab utama komplain Wasup, karena app ini aktif mempromosikan "Pasang Aplikasi". Di tab Safari biasa, window.print() MEMANG membuka Print Options sheet, tapi menjadikannya file yang bisa dibagikan butuh langkah tidak jelas (beda dari desktop yang satu klik "Save as PDF"). (2) **Ditemukan TERPISAH lewat print-to-PDF Chromium SUNGGUHAN** (bukan dugaan): bug PDF berhalaman-ganda yang BUKAN cuma masalah iOS — lihat entri CSS @media print di bawah.

**Perbaikan PDF/cetak berhalaman-ganda** (CSS `@media print`, `frontend/src/index.css` + `InvoiceModal.tsx` + `thermalPrint.ts`) — sebelum perbaikan ini, "Nota / PDF" menghasilkan PDF 4 HALAMAN dengan nota yang SAMA PERSIS diulang tiap halaman, di viewport mobile (390px) MAUPUN desktop (1280px) — dikonfirmasi lewat `page.pdf()` Chromium sungguhan, bukan `emulateMedia()` saja. Akar masalah: `body * { visibility: hidden }` (lama) tidak membuang TINGGI layout elemen lain (navbar, daftar transaksi, dst -- tetap ribuan px), sementara `#print-invoice-root` diposisikan absolute -- browser print engine menggambar ulang elemen itu di tiap halaman yang "muat" dalam tinggi dokumen semu itu. **Fix**: konten cetak di-render SEKALI sebagai elemen React (`notaBody` di `InvoiceModal.tsx`), dipakai DUA kali -- pratinjau layar (`#nota-preview`, visual TIDAK berubah) dan `createPortal()` LANGSUNG ke `document.body` (`#print-invoice-root`, `hidden print:block`). CSS diganti total: `body > *:not(#print-invoice-root):not(#print-thermal-root) { display: none !important }` (display:none, BUKAN visibility:hidden -- membuang tinggi layout-nya sungguhan) + `#print-invoice-root { position: static }`. `#print-thermal-root` (`thermalPrint.ts`, struk thermal jalur browser USB/AirPrint, SUDAH LAMA di-append langsung ke `document.body`) ikut dikecualikan di aturan global yang sama, style suntikannya disederhanakan jadi cuma `@page` ukuran kertas (visibility/positioning sudah ditangani aturan global, tidak diulang lagi di sana). Diverifikasi: nota pendek 1 halaman di 390px DAN 1280px, nota panjang dari Riwayat (cetak ulang) tetap 1 halaman, pratinjau layar identik sebelum/sesudah.

Lebar tetap 1080px potret, tinggi menyesuaikan isi.

**Logo lintas-domain (R2)**: `fetchLogoAsDataUrl(url)` fetch logo sebagai blob lalu dikonversi ke data URL SEBELUM digambar ke canvas (bukan langsung `drawImage` dari `<img src="https://...">`) — mencegah canvas tainted. `null` kalau fetch gagal (CORS/offline/404), nota tetap digambar TANPA logo (regresi aman, bukan gagal total). **TEMUAN PENTING (belum ada solusinya di sesi ini, perlu keputusan infra)**: diverifikasi lewat `curl -I` langsung ke `image.sewalog.com` — domain R2/CDN itu TIDAK mengirim header `Access-Control-Allow-Origin` sama sekali, jadi `fetchLogoAsDataUrl()` SELALU gagal di production juga (bukan cuma masalah dev lokal), logo vendor TIDAK PERNAH ikut tergambar di gambar Bagikan Nota sampai CORS diaktifkan di sisi R2/Cloudflare untuk origin app. Ini BEDA dari `shareCard.ts` (OG image Etalase, backend) yang aman karena fetch logo dilakukan SERVER-SIDE (tidak kena CORS browser sama sekali) -- Bagikan Nota genuinely butuh fetch CLIENT-SIDE (brief eksplisit minta canvas di browser, bukan render server), jadi masalah CORS ini nyata dan perlu fix infra terpisah, bukan sesuatu yang bisa diperbaiki murni di kode frontend.

Ulasan pengguna** — kartu "Ulasan untuk Sewalog" di tab Langganan (owner-only lewat gate tab yang sudah ada), teks ≤1.000 karakter + bintang 1–5 opsional, bisa diubah kapan saja (`business_reviews`, upsert langsung tanpa RPC — RLS `is_owner_of()` sudah cukup). ## 7. Skema database

Skema lengkap dan RLS policy final ada di `skema-final.sql` (bawa ke folder migrations). Poin-poin kunci:

- **Multi-tenant dari awal** — setiap vendor adalah satu baris `businesses`, semua tabel operasional di-scope via `business_id`, diisolasi lewat Postgres RLS berbasis `auth.uid() = businesses.owner_id`.
- **`business_profiles` dan `marketplace_consents` dipisah dari `businesses`** — cuma terisi kalau vendor eksplisit opt-in ke marketplace nanti. `marketplace_consents` bersifat append-only (riwayat persetujuan, bukan satu status yang ditimpa) — jangan buat policy `update`/`delete` untuk tabel ini.
- **Tabel wilayah (`provinces`, `regencies`) mencakup seluruh Indonesia** (38 provinsi, 514 kota/kabupaten — migration 033, Oktober 2026). Diperluas dari scope awal "cuma Malang Raya" setelah ada sinyal inbound nyata: vendor rental di luar Malang Raya DM lewat Instagram nanya soal app ini, dan field "Kota" yang dikunci ke 3 baris Malang Raya secara literal menghalangi vendor non-Malang Raya mengisi profil usahanya sendiri. Sumber data: cahyadsn/wilayah (lihat memory `reference-national-wilayah-data-sources`), sesuai Kepmendagri terbaru — idempotent terhadap 3 baris Malang Raya yang sudah ada sejak awal (nama persis sama, tidak terduplikasi lewat `on conflict`). **Level kecamatan diimpor di migration 052** (November 2026, tabel `districts`, 7.285 baris, sumber & Kepmendagri sama, simpan `code` Kemendagri mis. `35.73.05`) — keputusan Andi 9 Nov 2026: (a) ditampilkan di Etalase publik ("Kec. Lowokwaru, Kota Malang") supaya pelanggan tahu lokasi rental lebih persis, (b) disiapkan untuk **rekap per wilayah dengan cakupan lebih kecil** dari kota/kabupaten (rekapnya sendiri BELUM dibangun). Kolom `businesses.district_id` & `public_pages.district_id` sifatnya OPSIONAL (nullable, rental lama tidak wajib mengisi), dengan FK komposit `(district_id, regency_id)` supaya kecamatan selalu milik kota yang dipilih. Dropdown jadi tiga tingkat (Provinsi → Kota/Kabupaten → Kecamatan), kecamatan di-fetch per kota (`useDistricts()`), bukan sekaligus. Level desa/kelurahan tetap TIDAK diimpor. Dengan 514 pilihan kota/kabupaten, dropdown Kota di Info Usaha & Etalase Online jadi dua tingkat (Provinsi → Kota/Kabupaten, `RegencySelect.tsx` + `useRegencies.ts`) supaya tetap gampang dicari di HP, bukan satu `<select>` datar diurut nama.

  **Catatan konsistensi yang PENTING diingat**: ini cuma memperluas data referensi wilayah (field "Kota" di profil usaha) — BUKAN validasi bahwa app ini sudah siap dipakai vendor di luar WIB. Soal zona waktu ini sudah ditutup lewat setting zona waktu per rental (migration 053, lihat bagian 4) — tapi pengaturannya MANUAL oleh owner: vendor WITA/WIT yang belum menggantinya tetap dihitung WIB.
- **Tidak ada tabel `availability`** — dihitung dari agregasi `booking_items` + `bookings.status`, lihat query di bagian bawah `skema-final.sql`.
- **PostgREST `max_rows` = 1.000 (dikonfirmasi lewat Settings → API)** — query yang hasilnya lebih dari ini DIAM-DIAM terpotong, tanpa error. Brief skala data 2026-11-11 menemukan `fetchActiveBookingItems()` (dipakai Kalender, Catat Transaksi, Ubah Jadwal, Perpanjang) sebelumnya mengambil SEMUA `booking_items` lintas business tanpa filter sama sekali — risiko nyata salah hitung stok/double-booking begitu data lintas vendor lewat 1.000 baris. **Aturan wajib untuk query baru yang hasilnya berpotensi besar** (bukan dibatasi `.limit()` kecil yang disengaja seperti pencarian pelanggan): filter eksplisit `business_id` (jangan andalkan RLS saja), dan paginasi lewat `.range()` berulang sampai benar-benar habis dengan `.order()` pada kolom unik+deterministik (mis. `id`, atau `start_date` lalu `id` sebagai tie-breaker) — tanpa urutan deterministik, PostgREST tidak menjamin halaman berikutnya konsisten, baris bisa dobel atau terlompati. Pola referensi: `fetchAllPages()` di `backend/src/lib/availability.ts` dan paginasi `useHistory.ts` (Riwayat/rekap/ekspor). Query independen (mis. beberapa kelompok status, atau chunk `.in(id)`) dijalankan paralel lewat `Promise.all` (dibatasi concurrency kalau jumlah chunk-nya bisa besar), bukan berurutan — latency didominasi round-trip jaringan, bukan waktu eksekusi di Postgres.
- **Migration 058** menambah indeks (`business_id`+`start_date`, `business_id`+`status` di `bookings`; `booking_id` di `booking_items`/`deposits`/`penalties`/`booking_status_history`/`booking_reschedules`; `item_id` di `booking_items`) — sebelum ini, keenam tabel itu cuma punya primary key, jadi filter `business_id`/`booking_id` full table scan. Cek `pg_indexes` dulu sebelum menambah indeks baru di tabel yang sama supaya tidak dobel.
- **Migration 064** menambah `bundles`/`bundle_items` (Paket Alat, lihat bagian 6) — RLS select member, insert/update member digerbang `business_is_writable()` (bukan `is_owner_of`), delete member — pola sama `items` (migration 044), direvisi dari draf awal "owner-write" setelah dicek ulang bahwa `items` sendiri juga member-writable. Plus trigger `check_bundle_item_business()` (SECURITY INVOKER) menolak `bundle_items.item_id` yang bukan milik business sama dengan bundle-nya (RLS `WITH CHECK` saja tidak bisa membandingkan ke tabel `items` lain per baris). 4 kolom penanda nullable di `booking_items`/`booking_request_items`. `apply_booking_item_changes` (migration 061, Ubah Alat) di-create-or-replace ulang supaya ikut menulis kolom penanda ini.
- **Migration 065** (Paket Alat Tahap 2, lihat bagian 6) — CREATE OR REPLACE 3 fungsi publik, TIDAK ada tabel/kolom baru: `get_public_page()` (+key `'bundles'`), `create_booking_request()` (signature sama, elemen `p_items` boleh bawa 4 field bundle_* opsional + 2 validasi defense-in-depth baru), `get_booking_request_status()` (items ikut bawa bundle_name/bundle_instance_id/bundle_quantity). Field lama ketiganya + grant/revoke dipertahankan persis, diverifikasi curl anon diff-key sebelum dijalankan Andi.
- **Migration 066** (Barang Jual v1, lihat bagian 6) — 2 tabel baru `sale_items`/`booking_sale_items` (RLS: `booking_sale_items` SELECT-ONLY untuk member, tidak ada insert/update/delete langsung — satu-satunya jalur tulis adalah 3 RPC SECURITY DEFINER baru: `add_sale_item_stock`, `apply_new_booking_sale_items`, `apply_booking_item_and_sale_changes`, plus `restore_sale_item_stock_for_booking` untuk Batalkan). Tidak menyentuh `items`/`booking_items`/`usedUnitsOn()` sama sekali.
- **Migration 067** (Pelunasan + Nota Cetak Ulang + Batalkan/Void, lihat bagian 6) — tabel baru `booking_payments` (append-only, RLS SELECT-ONLY member, satu-satunya jalur tulis: trigger `log_initial_dp_payment()` AFTER INSERT ON `bookings` + RPC `add_booking_payment()`), kolom baru `bookings.dp_method` (nullable) dan `booking_status_history.reason` (nullable, baris lama tetap null). ## 8. Non-goals (sengaja belum dikerjakan)

- Marketplace publik / listing lintas vendor (Rimbasewa) — pencarian/browsing lintas vendor, perbandingan antar vendor, sistem matching. Etalase Online (bagian 6) murni satu halaman per satu vendor dari data yang sudah mereka input sendiri, bukan cikal-bakal ini.
- Native mobile app (Android/iOS)
- Offline-first / PWA caching agresif
- Manajemen multi-cabang / multi-karyawan per vendor
- Level desa/kelurahan di data wilayah — kecamatan sudah ada sejak migration 052 (lihat bagian 7), tapi desa/kelurahan belum ada fitur yang butuh presisi sampai level itu, tunda sampai ada kebutuhan nyata, bukan ditambah "supaya lengkap" semata.
- **Toko online berbayar per-vendor + payment gateway/checkout** (`app.sewalog.com/[nama-toko]` dengan transaksi/pembayaran online sungguhan, bukan cuma etalase info) — dievaluasi Agustus 2026, **ditunda bukan ditolak**. Alasan & syarat lengkap sebelum dibangun ada di `research/online-checkout-payment-roadmap-2026-08.md` (ringkas: nol bukti kebutuhan nyata dari vendor pilot, integrasi pembayaran Bilbo-Outdoors sendiri — kasus lebih sederhana — belum stabil untuk pelanggan asli, dan pertanyaan lisensi PJP dari Bank Indonesia belum terjawab, butuh opini hukum tertulis sebelum lanjut). Ada tab **Toko Online** (owner-only) di UI sebagai fake-door — cuma penjelasan rencana + tombol "Tertarik? Kasih Tahu Kami" ke WhatsApp, bukan fitur sungguhan — dipakai buat lihat sinyal minat vendor pilot secara murah sebelum commit ke pembangunan aslinya (syarat #2 di roadmap). **Tab ini disembunyikan dari Navbar sejak 2 Nov 2026** (permintaan Andi, lihat bagian 6) karena maknanya sudah tumpang-tindih dengan Pesanan Online — komponen & Panduan-nya tetap ada di kode, tinggal diaktifkan lagi lewat satu flag kalau sinyal minat vendor pilot ingin digali ulang nanti. **Catatan: halaman info/katalog publik per-vendor TANPA pembayaran sudah dibangun terpisah sebagai fitur "Etalase Online" (lihat bagian 6)** — non-goal di baris ini murni soal transaksi/pembayaran online sungguhan, bukan soal ada-tidaknya halaman publik itu sendiri. Catatan tambahan: formulir "Pesanan Online dari Etalase" (lihat bagian 6) BUKAN pengecualian dari non-goal ini — formulir itu murni mempercepat alur konfirmasi manual yang sudah ada (WA/formulir → Catat Transaksi), tidak ada uang yang berpindah lewat Sewalog sama sekali (halaman statusnya cuma menampilkan info bayar milik vendor sendiri), beda sifat dari toko online+payment gateway yang non-goal ini bicarakan.
